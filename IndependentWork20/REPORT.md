# Звіт до самостійної роботи №20

**Тема:** Реалізація exponential backoff


## Реалізація

Клас `RetryPolicy` має приватні поля `_maxRetries`, `_initialDelay`, `_jitterFactor` і узагальнений метод `Execute<T>(Func<T> operation, Func<Exception, bool>? shouldRetry = null)`, тому підходить для будь-якої операції з будь-яким типом результату.

Затримка обчислюється за формулою з методички:

```csharp
public TimeSpan CalculateDelay(int retryAttempt)
{
    double jitter = 1 + Random.Shared.NextDouble() * _jitterFactor * 2 - _jitterFactor;
    return _initialDelay * Math.Pow(2, retryAttempt) * jitter;
}
```

`Random.Shared.NextDouble()` повертає число з [0; 1), тому множник `jitter` випадково лежить у межах [1 − jitterFactor; 1 + jitterFactor), тобто ±20% при `jitterFactor = 0.2`. `Random.Shared` потокобезпечний, тож політику можна використовувати з кількох потоків одночасно.

Основний цикл:

```csharp
for (int attempt = 0; ; attempt++)
{
    try
    {
        Log($"Спроба {attempt + 1} з {_maxRetries + 1}");
        T result = operation();
        Log($"Спроба {attempt + 1}: успіх");
        return result;
    }
    catch (Exception ex)
    {
        Log($"Спроба {attempt + 1}: невдача — {ex.GetType().Name}: {ex.Message}");

        bool retryable = shouldRetry?.Invoke(ex) ?? true;
        if (!retryable)
        {
            Log("Виняток не підлягає повтору (shouldRetry = false) — передаємо його далі");
            throw;
        }

        if (attempt >= _maxRetries)
        {
            Log($"Усі {_maxRetries} повторні спроби вичерпано — передаємо виняток далі");
            throw;
        }

        TimeSpan delay = CalculateDelay(attempt);
        Log($"Очікування {delay.TotalMilliseconds:F0} мс перед повторною спробою №{attempt + 1}");
        Thread.Sleep(delay);
    }
}
```

- `throw;` (без змінної) передає далі **оригінальний** виняток зі збереженим стеком викликів, тож викликач обробляє той самий тип помилки, що й без політики.
- Якщо `shouldRetry` не передано, повторюються всі винятки; якщо передано — лише ті, для яких він повертає `true`.
- Конструктор перевіряє параметри: від'ємна кількість повторів, нульова затримка чи `jitterFactor` ≥ 1 (який дав би нульову або від'ємну затримку) відкидаються з `ArgumentOutOfRangeException`.

**Обрані параметри:** `maxRetries = 4`, `initialDelay = 250 мс`, `jitterFactor = 0.2`. Базові затримки: 250 → 500 → 1000 → 2000 мс, усього до ~3,75 с очікування (з jitter — від 3 до 4,5 с). Для інтерактивного застосунку довше чекати не варто.

## Демонстрація

Операція — запит середнього балу до сервера електронного журналу коледжу (`GradebookServer`), який після оновлення кілька перших запитів відповідає `TimeoutException`.

1. **Таблиця затримок** — для кожного повтору виводиться базова затримка і три випадкові значення з jitter. Видно, що затримка подвоюється, а значення розкидані в межах ±20%.
2. **Успіх після кількох спроб** — сервер двічі відповідає тайм-аутом. У лозі: спроба 1 невдала → очікування ~250 мс → спроба 2 невдала → очікування ~500 мс → спроба 3 успішна, `середній бал = 4,6 (запитів до сервера: 3)`. Мітки часу підтверджують реальні паузи.
3. **Остаточна невдача** — сервер недоступний постійно. Після 5 спроб (1 + 4 повтори) у лозі з'являється `Усі 4 повторні спроби вичерпано`, і `TimeoutException` перехоплюється в `Main`: `Остаточна невдача після 5 запитів`.
4. **shouldRetry** — передано фільтр `IsTransient` (тайм-аут, мережеві помилки, помилки вводу-виводу). Перша помилка (`TimeoutException`) повторюється, друга (`ArgumentException` — порожнє ім'я студента) — ні: політика одразу передає її далі (`Запитів до сервера: 2 — зайвих повторів не було`).

## Висновок: межі застосування патерну Retry з exponential backoff

Retry з експоненційною затримкою доречний для **тимчасових** збоїв, які зникають самі: короткочасна недоступність мережі, перевантаження сервера (503, 429), тайм-аут з'єднання, конфлікт блокувань у БД. Експоненційна затримка дає сервісу час відновитися і не «добиває» його частими запитами, а jitter розносить у часі повтори від багатьох клієнтів.

Патерн **не підходить**, а то й шкідливий, у таких випадках:
- **Постійні помилки** — некоректні дані запиту (`ArgumentException`, 400), відсутність прав (401/403), неіснуючий ресурс (404), помилки в коді. Повтор дасть той самий результат, лише пізніше. Тому потрібен `shouldRetry`.
- **Неідемпотентні операції** — оплата, створення замовлення, відправлення листа. Якщо операція виконалась, а втратилась лише відповідь, повтор продублює її. Такі операції можна повторювати тільки з ключем ідемпотентності.
- **Тривалі збої.** Якщо сервіс «лежить» хвилинами, Retry лише змушує користувача довше чекати і додає навантаження. Тут доречний Circuit Breaker.
- **Жорсткі вимоги до часу відповіді.** Сумарна затримка росте експоненційно (з 4 повторами — до кількох секунд), тож кількість повторів і максимальну затримку треба обмежувати, а для інтерфейсу користувача краще показати «спробуйте пізніше».
- **Вкладені повтори.** Якщо Retry є на кількох рівнях (клієнт, сервіс, драйвер БД), кількість реальних спроб перемножується, і замість 5 запитів може вийти 125.

Також ця реалізація використовує `Thread.Sleep`, тому під час очікування блокує потік. Для серверних застосунків краще асинхронна версія з `await Task.Delay(...)` і підтримкою `CancellationToken`, або готова бібліотека Polly.

## Відповіді на контрольні запитання

1. **Чому експоненційна затримка ефективніша за фіксовану?** Короткі збої вона долає швидко (перша пауза мала), а для довших дає сервісу дедалі більше часу на відновлення. Загальна кількість запитів до проблемного сервісу при цьому значно менша, ніж при частих повторах з фіксованою паузою, які лише посилюють перевантаження.
2. **Навіщо jitter?** Якщо багато клієнтів отримали помилку одночасно, без jitter вони повторять запити теж одночасно — через 250, 500, 1000 мс. Ці синхронні хвилі навантаження знову перевантажать сервіс. Випадкове відхилення ±20% розносить повтори в часі і вирівнює навантаження.
3. **Роль shouldRetry.** Він відділяє тимчасові помилки, які варто повторювати, від постійних, які повторювати безглуздо або небезпечно. Делегат робить політику гнучкою: одна й та сама `RetryPolicy` може використовуватись для різних операцій з різними правилами, без змін самого класу.
4. **Коли повтор небезпечний і його слід заборонити?** Для неідемпотентних операцій (платежі, створення записів, відправлення повідомлень) без механізму ідемпотентності. Також для помилок валідації та авторизації, для винятків, що свідчать про помилку в коді (`NullReferenceException`), і коли операцію скасував сам користувач (`OperationCanceledException`).
