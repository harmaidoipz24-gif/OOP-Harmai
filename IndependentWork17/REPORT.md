# Звіт до самостійної роботи №17

**Тема:** LINQ pipelines: ETL та аналітика


## 1. Модель даних і етапи ETL

Сутності: `Product` (Id, Name, Category, UnitPrice), `Customer` (Id, Name, City), `Sale` (Id, ProductId, Quantity, SaleDate, CustomerId).

| Етап ETL | Як реалізовано |
|---|---|
| **Extract** | `DataGenerator` створює 50 товарів (5 категорій × 10), 80 клієнтів з 8 міст і 5000 продажів за січень 2025 — жовтень 2026. `Random(2026)` з фіксованим seed робить дані однаковими при кожному запуску. |
| **Transform** | чотири LINQ-пайплайни: з'єднання (`Join`), групування (`GroupBy`), агрегація (`Sum`, `Count`, `Aggregate`), сортування й відбір (`OrderBy`, `Take`). |
| **Load** | результати матеріалізуються через `ToList()` у типізовані записи (`CategoryTopProducts`, `CityRevenue`, `MonthlySales`, `CustomerSummary`) і виводяться у вигляді звіту. |

Кожен пайплайн оформлено окремим методом із промовистою назвою, тож `Main` займає кілька рядків.

## 2. Опис пайплайнів

### Пайплайн 1. Найпопулярніші продукти за категоріями

```csharp
return _sales
    .GroupBy(s => s.ProductId)
    .Select(g => new { ProductId = g.Key, TotalQuantity = g.Sum(s => s.Quantity) })
    .Join(_products,
          stat => stat.ProductId,
          product => product.Id,
          (stat, product) => new { product.Name, product.Category, stat.TotalQuantity })
    .GroupBy(x => x.Category)
    .Select(g => new CategoryTopProducts(
        g.Key,
        g.OrderByDescending(x => x.TotalQuantity)
         .ThenBy(x => x.Name)
         .Take(3)
         .Select(x => new ProductQuantity(x.Name, x.TotalQuantity))
         .ToList()))
    .OrderBy(c => c.Category)
    .ToList();
```

- **Мета:** для кожної категорії знайти три товари з найбільшою кількістю проданих одиниць.
- **Оператори і чому саме вони:**
  - `GroupBy(ProductId)` + `Sum` — спершу агрегуємо 5000 продажів до 50 рядків «товар — сума». З'єднувати з довідником товарів вигідніше вже після агрегації: `Join` обробляє 50 рядків замість 5000.
  - `Join` — додає назву і категорію з довідника товарів.
  - друге `GroupBy(Category)` — розбиває товари за категоріями.
  - `OrderByDescending` + `ThenBy(Name)` + `Take(3)` — топ-3 всередині кожної групи; `ThenBy` робить результат однозначним, якщо кількості однакові.
  - `OrderBy(Category)` — стабільний порядок категорій у звіті.

### Пайплайн 2. Загальний дохід за містами клієнтів

```csharp
return _sales
    .Join(_products, s => s.ProductId, p => p.Id,
          (s, p) => new { s.CustomerId, Revenue = s.Quantity * p.UnitPrice })
    .Join(_customers, x => x.CustomerId, c => c.Id,
          (x, c) => new { c.City, x.Revenue })
    .GroupBy(x => x.City)
    .Select(g => new CityRevenue(g.Key, g.Sum(x => x.Revenue), g.Count()))
    .OrderByDescending(c => c.Revenue)
    .ToList();
```

- **Мета:** порівняти міста за доходом.
- **Оператори:** два `Join` — дохід потребує ціни з `Product`, а місто зберігається в `Customer`. У проєкції першого `Join` одразу обчислюється `Quantity * UnitPrice`, і далі йдуть лише потрібні поля (`CustomerId`, `Revenue`), а не цілі об'єкти. `GroupBy(City)` + `Sum` агрегують дохід, `Count` показує кількість продажів, `OrderByDescending` впорядковує від найприбутковішого міста.
- Той самий запит у синтаксисі запитів (query syntax) — для порівняння читабельності:

```csharp
from s in _sales
join p in _products on s.ProductId equals p.Id
join c in _customers on s.CustomerId equals c.Id
group s.Quantity * p.UnitPrice by c.City into g
orderby g.Sum() descending
select new CityRevenue(g.Key, g.Sum(), g.Count());
```

### Пайплайн 3. Продажі за місяцями та роками

```csharp
return _sales
    .Join(_products, s => s.ProductId, p => p.Id,
          (s, p) => new { s.SaleDate, s.Quantity, Revenue = s.Quantity * p.UnitPrice })
    .GroupBy(x => new { x.SaleDate.Year, x.SaleDate.Month })
    .Select(g => new MonthlySales(
        g.Key.Year,
        g.Key.Month,
        g.Sum(x => x.Quantity),
        g.Sum(x => x.Revenue)))
    .OrderBy(m => m.Year)
    .ThenBy(m => m.Month)
    .ToList();
```

- **Мета:** побачити динаміку продажів у часі (22 місяці).
- **Оператори:** `Join` — для ціни товару. `GroupBy` за **складеним ключем** — анонімним типом `{ Year, Month }`. Анонімні типи автоматично реалізують `Equals` і `GetHashCode` за всіма полями, тому групування за двома полями працює без власного comparer. Два `Sum` рахують одиниці та дохід, `OrderBy(Year).ThenBy(Month)` дає хронологічний порядок (сортувати лише за місяцем було б помилкою — січні 2025 і 2026 стояли б поруч).

### Пайплайн 4 (додатковий). Найкращі клієнти 2026 року

```csharp
return _sales
    .Where(s => s.SaleDate >= from)
    .Join(_products, s => s.ProductId, p => p.Id,
          (s, p) => new { s.CustomerId, p.Category, Revenue = s.Quantity * p.UnitPrice })
    .GroupBy(x => x.CustomerId)
    .Join(_customers, g => g.Key, c => c.Id, (g, c) => new { Customer = c, Purchases = g.ToList() })
    .Select(x => new CustomerSummary(
        x.Customer.Name,
        x.Customer.City,
        x.Purchases.Sum(p => p.Revenue),
        x.Purchases.Count,
        x.Purchases.Select(p => p.Category).Distinct().Count(),
        x.Purchases
            .GroupBy(p => p.Category)
            .Select(g => new { Category = g.Key, Spent = g.Sum(p => p.Revenue) })
            .Aggregate((best, next) => next.Spent > best.Spent ? next : best)
            .Category))
    .OrderByDescending(c => c.TotalSpent)
    .Take(5)
    .ToList();
```

- **Мета:** знайти п'ять клієнтів, які витратили найбільше з початку 2026 року, і для кожного — кількість покупок, кількість різних категорій та категорію, на яку він витратив найбільше.
- **Оператори:** `Where` фільтрує **на самому початку**, щоб далі обробляти менше даних. Далі `Join`, `GroupBy` за клієнтом, `Join` з клієнтами, `Distinct().Count()` — кількість різних категорій, `Aggregate` — пошук максимуму за один прохід з поверненням усього елемента, а не лише значення. Наприкінці `OrderByDescending` + `Take(5)`.

## 3. Вимірювання продуктивності

Для кожного пайплайну створюється **окремий** `Stopwatch`. Вимірюються два значення:
- **перший запуск** — включає JIT-компіляцію коду пайплайну і анонімних типів;
- **середній час з 50 повторних запусків** — «прогрітий» стан, відображає саму роботу LINQ.

| Пайплайн | Перший запуск, мс | Середній повторний, мс |
|---|---|---|

| 2. Дохід за містами | | |
| 3. Продажі за місяцями | | |
| 4. Найкращі клієнти | | |

Запуск: `dotnet run -c Release`.

### Аналіз: які фактори впливають на час виконання

1. **JIT-компіляція.** Перший запуск кожного пайплайну помітно довший за повторні: .NET компілює LINQ-ітератори, лямбди й анонімні типи в машинний код при першому використанні. Тому один вимір без прогріву не показує реальної швидкості.
2. **Кількість `Join`.** `Join` будує хеш-таблицю (`Lookup`) з другої колекції і проходить першу — O(n + m). Пайплайни 2 і 4 мають по два `Join` і обробляють усі 5000 продажів, тому зазвичай повільніші за пайплайн 1.
3. **Порядок операторів.** У пайплайні 1 агрегація стоїть до `Join`, тому з'єднуються 50 рядків, а не 5000. У пайплайні 4 `Where` на початку відкидає продажі 2025 року ще до `Join` і `GroupBy`. Ранні фільтрація та агрегація — найефективніша оптимізація LINQ.
4. **Створення об'єктів.** Кожен `Select` у анонімний тип створює новий об'єкт для кожного рядка, а `ToList()` всередині групи (пайплайн 4) копіює дані. Це навантаження на пам'ять і збирач сміття (GC); паузи GC можуть «стрибком» збільшити окремий вимір.
5. **Тип `decimal`.** Арифметика з `decimal` повільніша, ніж з `double`, бо виконується програмно, а не процесором. Зате вона точна для грошей.
6. **Сортування.** `OrderBy` — O(n log n), але тут сортуються вже агреговані результати (8 міст, 22 місяці), тож внесок малий.
7. **Зовнішні умови:** конфігурація Debug/Release, інші програми, режим енергозбереження процесора. Через це цифри коливаються між запусками, тому порівнюються середні значення.

Загалом обробка 5000 записів усіма пайплайнами займає частки мілісекунди — мілісекунди. Для такого обсягу продуктивність LINQ з запасом достатня.

## 4. Висновки щодо ефективності LINQ для ETL та аналітики

- **Виразність.** Кожен пайплайн читається як опис бізнес-задачі («згрупуй, з'єднай, підсумуй, відсортуй»). Аналогічний код на циклах потребував би ручних словників для групування, вкладених циклів для з'єднання і тимчасових списків — у кілька разів більше рядків і більше місць для помилок.
- **Продуктивність достатня** для типових обсягів даних у пам'яті (тисячі — сотні тисяч записів). `Join` і `GroupBy` всередині використовують хеш-таблиці, тож мають лінійну складність. Накладні витрати LINQ (делегати, ітератори, проміжні об'єкти) роблять його повільнішим за ретельно написаний цикл, але зазвичай на відсотки, а не в рази.
- **Порядок операторів важливий:** фільтрувати й агрегувати якомога раніше, з'єднувати — якомога пізніше і з меншими наборами.
- **Відкладене виконання.** Запит виконується лише під час перебирання, тому для вимірювання часу і для повторного використання результату його треба матеріалізувати через `ToList()`; інакше кожен перебір запускатиме весь пайплайн заново.
- **Межі застосування.** Для мільйонів записів варто розглянути PLINQ (паралельна обробка), а для даних у базі — переносити обчислення в SQL (через `IQueryable` в Entity Framework той самий LINQ-код перетворюється на SQL-запит). Для справжніх ETL-систем з гігабайтами даних використовують спеціалізовані інструменти; LINQ доречний для аналітики на рівні застосунку.

## Відповіді на контрольні запитання

1. **Переваги LINQ для ETL порівняно з циклами.** Декларативний і коротший код, який описує, *що* треба отримати, а не *як*. Є готові оптимізовані оператори з'єднання й групування, ланцюжки легко комбінувати і змінювати, менше проміжних змінних і помилок, а один стиль коду працює і для колекцій у пам'яті, і для баз даних через `IQueryable`.
2. **Чому поєднують Join, GroupBy, Select та OrderBy.** Аналітичні дані зазвичай розкладені по кількох таблицях (продажі, товари, клієнти), тож спершу їх треба з'єднати (`Join`). Далі агрегувати за потрібною ознакою (`GroupBy` + `Sum`), вибрати потрібні поля або обчислити показники (`Select`) і впорядкувати для звіту (`OrderBy`). Кожен оператор виконує один крок, і разом вони утворюють повний звіт.
3. **Фактори продуктивності.** Обсяг даних, порядок операторів (рання фільтрація й агрегація), кількість `Join` і їхня реалізація, створення проміжних об'єктів і навантаження на GC, повторне перебирання невиконаного запиту через відкладене виконання, вкладені запити всередині `Select` (O(n²)), JIT при першому запуску, тип даних (`decimal` проти `double`).
4. **Як перевірити, що пайплайн читабельний і підтримуваний.** Кожен пайплайн винесено в окремий метод з промовистою назвою; кожен крок займає окремий рядок; проміжні результати мають зрозумілі імена полів; результат — типізований `record`, а не анонімний тип. Коректність перевіряється на невеликих даних, де результат можна порахувати вручну, або юніт-тестами з фіксованими даними. Корисно також мати стабільне сортування (`ThenBy`), щоб результат не змінювався між запусками.
