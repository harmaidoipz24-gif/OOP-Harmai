# Звіт до самостійної роботи №15

**Тема:** Делегати й лямбда-вирази: власні утиліти для колекцій


## Реалізація

Статичний клас `CollectionUtils` містить чотири узагальнені методи, кожен з яких отримує поведінку через делегат:

| Метод | Делегат | Що робить | Аналог у LINQ |
|---|---|---|---|
| `Map<TSource, TResult>` | `Func<TSource, TResult>` | перетворює кожен елемент | `Select` |
| `MaxBy<T, TKey>` | `Func<T, TKey>` + `where TKey : IComparable<TKey>` | шукає елемент з найбільшим ключем | `MaxBy` (.NET 6+) |
| `Filter<T>` | `Predicate<T>` | відбирає елементи за умовою | `Where` |
| `ForEach<T>` | `Action<T>` | виконує дію для кожного елемента | `List<T>.ForEach` (для `IEnumerable<T>` у LINQ немає) |

```csharp
public static IEnumerable<T> Filter<T>(IEnumerable<T> collection, Predicate<T> predicate)
{
    ArgumentNullException.ThrowIfNull(collection);
    ArgumentNullException.ThrowIfNull(predicate);

    List<T> result = new List<T>();
    foreach (T item in collection)
    {
        if (predicate(item))
            result.Add(item);
    }
    return result;
}

public static void ForEach<T>(IEnumerable<T> collection, Action<T> action)
{
    ArgumentNullException.ThrowIfNull(collection);
    ArgumentNullException.ThrowIfNull(action);

    foreach (T item in collection)
    {
        action(item);
    }
}
```

`MaxBy` порівняно з прикладом у методичці змінено: замість `default(T)` і прапорця `first` перший елемент береться з перелічувача, а для порожньої колекції кидається `InvalidOperationException`. Інакше для порожнього `List<int>` метод «тихо» повертав би `0`, наче це справжній максимум.

```csharp
using IEnumerator<T> enumerator = collection.GetEnumerator();
if (!enumerator.MoveNext())
    throw new InvalidOperationException("Колекція порожня — максимального елемента немає.");

T maxItem = enumerator.Current;
TKey maxKey = keySelector(maxItem);
```

Роботу показано на трьох різних колекціях: `List<Product>`, `List<int>` і `string[]`, а також на делегатах, збережених у змінних, і на іменованому методі замість лямбди.

## 1. Чому делегати корисні для створення таких утиліт?

Делегат — це посилання на метод, тобто «поведінка, яку можна передати як параметр». Завдяки цьому `CollectionUtils` відокремлює **загальний алгоритм** (обійти колекцію, зібрати результат, знайти максимум) від **конкретної логіки** (яку умову перевірити, яке поле взяти).

- Один метод `Filter` замінює десятки окремих методів: `GetExpensiveProducts`, `GetPositiveNumbers`, `GetShortWords`… Умова передається ззовні.
- Утиліти узагальнені й працюють з будь-якими типами: у програмі той самий `Map` перетворює `Product → string`, `int → int`, `int → string`, `string → int`, `double → string`.
- Кожен тип делегата документує намір: `Predicate<T>` — «перевірити умову» (повертає `bool`), `Func<T, TResult>` — «обчислити значення», `Action<T>` — «виконати дію», нічого не повертаючи.
- Поведінку можна зберегти у змінній і використати повторно (`Predicate<int> isEven = n => n % 2 == 0;`), передати іменований метод (`FormatSqrt`) або скласти ланцюжок `Filter → Map → ForEach`.

## 2. Як лямбда-вирази спрощують виклик цих методів?

Без лямбд для кожної умови довелося б писати окремий іменований метод десь у класі:

```csharp
private static bool IsExpensive(Product p) => p.Price > 1000;
...
CollectionUtils.Filter(products, IsExpensive);
```

З лямбдою логіка записується прямо в місці виклику, і код читається як речення:

```csharp
CollectionUtils.Filter(products, p => p.Price > 1000);
```

Крім того:
- **виведення типів**: компілятор сам визначає, що `p` — це `Product`, а `TResult` у `Map(products, p => p.Name)` — `string`, тож узагальнені параметри не треба вказувати вручну;
- **замикання**: лямбда може використовувати зовнішні змінні. У демонстрації `CollectionUtils.ForEach(numbers, n => sum += n)` змінює локальну змінну `sum` з методу `Main`;
- лямбда коротка, тому одну й ту саму утиліту зручно викликати з різними умовами: `MaxBy(products, p => p.Price)` і `MaxBy(products, p => p.Name.Length)`.

## 3. Порівняння з вбудованими LINQ-операторами

| Аспект | CollectionUtils | LINQ |
|---|---|---|
| Виклик | статичний: `CollectionUtils.Filter(list, ...)` | метод розширення: `list.Where(...)`, можна будувати ланцюжки `list.Where(...).Select(...)` |
| Виконання | **негайне**: результат одразу збирається в `List<T>` | **відкладене** (`yield return`): елементи обчислюються лише під час перебирання |
| Пам'ять | на кожному кроці створюється новий список | проміжних колекцій немає, елементи «протікають» через ланцюжок по одному |
| Делегат умови | `Predicate<T>` | `Func<T, bool>` (а також перевантаження з індексом елемента) |
| Порожня колекція у MaxBy | `InvalidOperationException` | для посилальних типів повертає `null`, для значущих — виняток |
| Оптимізації | немає | спеціальні шляхи для масивів і `List<T>`, об'єднання `Where().Select()` в один ітератор |
| Можливості | 4 операції | десятки операторів, `IQueryable` для перетворення в SQL (Entity Framework) |

Висновок: власні методи повторюють суть LINQ, адже `Select`, `Where`, `MaxBy` всередині теж просто викликають переданий делегат для кожного елемента. Реалізація їх власноруч допомагає зрозуміти, як LINQ влаштований. У робочому коді краще використовувати LINQ: він ліниво обчислюється, оптимізований, перевірений і знайомий кожному C#-розробнику. Свій `ForEach` для `IEnumerable<T>` має сенс, бо в LINQ такого немає, але Microsoft його свідомо не додала: LINQ орієнтований на запити без побічних ефектів, а для дій є звичайний `foreach`.

## Відповіді на контрольні запитання

1. **Чому делегати зручні для передавання поведінки в узагальнені методи?** Узагальнений метод не знає, з якими даними працюватиме, тож конкретну логіку (умову, перетворення, дію) він отримує ззовні через делегат. Один алгоритм обходу колекції обслуговує будь-які типи й будь-які умови, і дублювати код не треба.
2. **Різниця між Func, Action і Predicate.** `Func<T, TResult>` приймає аргумент і повертає результат (використано в `Map` і `MaxBy`). `Action<T>` приймає аргумент і нічого не повертає — для дій з побічним ефектом (`ForEach`). `Predicate<T>` приймає аргумент і повертає `bool` — спеціалізований делегат для перевірки умови (`Filter`); за змістом він рівний `Func<T, bool>`, але ці типи несумісні між собою без явного перетворення.
3. **Переваги поєднання generic-методів і лямбд.** Узагальнення дають типобезпечність і повторне використання для будь-яких типів, а лямбди — короткий запис логіки в місці виклику з автоматичним виведенням типів. Разом вони дозволяють одним рядком описати операцію над колекцією, яка без них зайняла б цикл на кілька рядків.
4. **Коли варто писати власні Map чи Filter, хоч є LINQ.** Під час навчання — щоб зрозуміти, як працює LINQ. Також коли потрібна поведінка, якої LINQ не дає: негайне виконання з гарантованим знімком даних, особлива обробка порожніх колекцій, логування чи перевірки на кожному кроці, операція, якої в LINQ немає (як `ForEach` для `IEnumerable<T>`), або середовище, де LINQ недоступний чи небажаний через виділення пам'яті (наприклад, гарячий цикл у Unity).
