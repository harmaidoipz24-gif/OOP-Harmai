# Звіт до самостійної роботи №18

**Тема:** PLINQ: дослідження продуктивності та безпеки


## 1. Опис експериментів

**Дані.** `List<int>` розміром 1 000 000, 5 000 000 і 10 000 000 елементів, заповнений випадковими числами від 1 до 5 000 000. `Random(12)` з фіксованим seed дає однакові дані для LINQ і PLINQ та між запусками.

**Обчислювально інтенсивна операція** — перевірка на просте число перебором дільників до √n і перетворення знайдених простих чисел:

```csharp
private static bool IsPrime(int n)
{
    if (n < 2) return false;
    if (n % 2 == 0) return n == 2;

    int limit = (int)Math.Sqrt(n);
    for (int divisor = 3; divisor <= limit; divisor += 2)
    {
        if (n % divisor == 0)
            return false;
    }
    return true;
}

private static double Transform(int n) => Math.Sqrt(n) * Math.Log(n);
```

```csharp
// LINQ
data.Where(IsPrime).Select(Transform).Sum();

// PLINQ
data.AsParallel().Where(IsPrime).Select(Transform).Sum();
```

Для простого числа близько 5 000 000 перевірка робить понад тисячу ділень, тому робота над кожним елементом достатньо «важка», щоб паралелізм окупився.

**Дешева операція** — для порівняння:

```csharp
data.Where(n => n % 3 == 0).Select(n => (long)n * 2).Sum();
data.AsParallel().Where(n => n % 3 == 0).Select(n => (long)n * 2).Sum();
```

**Методика:**
- Окремий `Stopwatch` для кожного виміру.
- Перед вимірюваннями — прогрів на 100 000 елементів, щоб JIT-компіляція і запуск пулу потоків не потрапили в результати.
- Програма перевіряє, що LINQ і PLINQ дали однаковий результат. Для суми `double` допускається відносна похибка 1e-9: у паралельному режимі числа додаються в іншому порядку, а додавання з плаваючою комою не асоціативне.
- Запуск у конфігурації Release: `dotnet run -c Release`. Програма виводить кількість логічних процесорів, бо від неї залежить можливе прискорення.

## 3. Аналіз: коли PLINQ швидший, а коли — ні

**Важка операція.** Тут PLINQ має бути помітно швидшим на всіх розмірах колекції. Перевірка кожного числа незалежна від інших, тому задача ідеально ділиться між ядрами: PLINQ розбиває колекцію на частини, обробляє їх у кількох потоках, а наприкінці складає часткові суми. Корисна робота на кожен елемент значно перевищує накладні витрати паралелізму. Прискорення обмежене кількістю ядер і зазвичай менше за неї, бо:
- частина роботи послідовна (розбиття даних, об'єднання результатів) — закон Амдала;
- роботи нерівномірні: прості числа перевіряються довго, складені — швидко, тож потоки завершують свої частини в різний час;
- логічні процесори з Hyper-Threading ділять одне фізичне ядро і не дають подвійного прискорення;
- одночасно працюють інші програми та сама ОС.

Зі збільшенням розміру колекції прискорення стає стабільнішим: фіксовані витрати на запуск паралельного запиту «розмазуються» на більшу кількість роботи.

**Дешева операція.** Тут PLINQ може бути приблизно таким самим або навіть повільнішим за LINQ, особливо на 1 млн елементів. Причина в тому, що операція `n % 3` займає наносекунди, а PLINQ витрачає час на:
- розбиття колекції на частини і координацію потоків;
- синхронізацію під час об'єднання результатів;
- конкуренцію потоків за пропускну здатність пам'яті — для простих операцій «вузьке місце» не процесор, а читання даних з RAM, і більше ядер не пришвидшують пам'ять.

У такому разі накладні витрати співмірні з корисною роботою або перевищують її.

**Вплив розміру колекції.** Час LINQ зростає майже лінійно з розміром (у 10 разів більше даних — приблизно в 10 разів довше). PLINQ на малих колекціях обтяжений фіксованими витратами, а на великих наближається до свого максимального прискорення. Саме тому порівнюються кілька розмірів: один вимір не показує, як змінюється вигода від паралелізму.

## 4. Побічні ефекти та потокобезпечність

### Як виникла проблема

Завдання: порахувати парні числа в колекції з 1 000 000 елементів. Наївна реалізація змінює спільну змінну зсередини PLINQ:

```csharp
int unsafeCounter = 0;
data.AsParallel().ForAll(n =>
{
    if (n % 2 == 0)
        unsafeCounter++;
});
```

Операція `unsafeCounter++` не атомарна. Вона складається з трьох кроків: прочитати значення, збільшити його, записати назад. Коли два потоки одночасно читають, наприклад, 1000, обидва записують 1001, і одне збільшення губиться (стан гонитви, *race condition*). Програма запускає цей код тричі. Кожного разу результат менший за правильний і **різний між запусками** — це головна ознака проблеми потокобезпечності. На одноядерному комп'ютері помилка могла б не проявитися, що робить її ще небезпечнішою.

Друга демонстрація — додавання в звичайний `List<int>` з кількох потоків. `List<T>.Add` змінює внутрішній масив і лічильник без синхронізації, тому елементи губляться або виникає виняток (`IndexOutOfRangeException` чи `ArgumentException`), коли два потоки одночасно розширюють масив. PLINQ загортає такий виняток в `AggregateException`.

### Як проблему виправлено

| Спосіб | Код | Коли підходить |
|---|---|---|
| `lock` | `lock (sync) { lockedCounter++; }` | будь-яка складна зміна спільного стану; але потоки стоять у черзі за блокуванням, тому це найповільніший варіант |
| `Interlocked` | `Interlocked.Increment(ref counter);` | атомарні операції над одним числом (лічильник, сума); апаратна атомарна інструкція без блокування, швидше за `lock` |
| `ConcurrentBag<T>` | `bag.Add(n);` | збирання елементів з кількох потоків у колекцію, коли порядок не важливий |
| **без побічних ефектів** | `data.AsParallel().Count(n => n % 2 == 0)` | **найкращий варіант**: кожен потік рахує свою частину, а PLINQ безпечно об'єднує результати |

Для лічильника найбільше підходить відмова від спільної змінної (`Count`). Якщо зміна спільного стану неминуча, обирається `Interlocked`, бо він атомарний і не блокує потоки. `lock` потрібен лише тоді, коли треба змінити кілька пов'язаних значень разом. Програма виводить час кожного варіанта: варіанти з синхронізацією на кожному елементі повільніші, бо потоки змагаються за одну змінну.

## 5. Висновки

1. PLINQ дає реальне прискорення для **обчислювально інтенсивних** операцій над **великими** колекціями, коли елементи обробляються незалежно. Максимальне прискорення обмежене кількістю ядер.
2. Для дешевих операцій і малих колекцій PLINQ може бути повільнішим за LINQ через накладні витрати на розподіл роботи й синхронізацію. Паралелізм — не безкоштовна оптимізація, і перед впровадженням його треба вимірювати.
3. Лямбди в PLINQ мають бути **чистими функціями** без побічних ефектів. Зміна спільних змінних чи непотокобезпечних колекцій дає неправильні, нестабільні результати, які важко відлагодити, бо помилка проявляється не щоразу.
4. Якщо побічний ефект потрібен, використовуються `Interlocked`, `lock` або потокобезпечні колекції (`ConcurrentBag`, `ConcurrentDictionary`). Але кращий шлях — переписати запит так, щоб результат об'єднувала сама PLINQ (`Count`, `Sum`, `Aggregate`, `ToList`).
5. Слід пам'ятати й інші особливості PLINQ: він не зберігає порядок елементів без `AsOrdered()`, а сума `double` може відрізнятися в останніх знаках через інший порядок додавання.

## Відповіді на контрольні запитання

1. **Коли PLINQ дає виграш?** Коли операція над кожним елементом обчислювально дорога, колекція велика, елементи обробляються незалежно, без спільного стану і без вимог до порядку, а на комп'ютері кілька ядер, не зайнятих іншою роботою.
2. **Чому побічні ефекти дають некоректні результати?** Лямбда виконується одночасно в кількох потоках, а неатомарні операції (`counter++`, `list.Add`) складаються з кількох кроків. Потоки перемежовують ці кроки й перезаписують зміни один одного (стан гонитви), тому оновлення губляться, колекції пошкоджуються або виникають винятки, причому результат щоразу різний.
3. **Навіщо кілька розмірів колекції?** Ефективність паралелізму залежить від співвідношення корисної роботи до фіксованих накладних витрат. На малому обсязі PLINQ може програвати, а на великому — вигравати, тож лише кілька вимірів показують тенденцію і поріг, з якого паралелізм окупається. Окремий вимір також може бути спотворений випадковою паузою GC чи іншою програмою.
4. **Що робити, якщо PLINQ повільніший?** Не використовувати PLINQ для цієї операції або обсягу даних: робота на елемент занадто дешева чи колекція замала. Можна спробувати збільшити «гранулярність» роботи (обробляти елементи блоками), прибрати синхронізацію з лямбди, перевірити кількість ядер і конфігурацію Release. Головний висновок — паралелізацію треба підтверджувати вимірюваннями, а не вмикати «про всяк випадок».
