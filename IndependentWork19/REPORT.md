# Звіт до самостійної роботи №19

**Тема:** Дизайн винятків і політики retry: теорія та кейси Polly


Проєкт використовує пакет `Polly.Core` 8.x з актуальним API `ResiliencePipelineBuilder`. Пакет підтягується автоматично під час `dotnet build` / `dotnet run`. Якщо треба додати його вручну: `dotnet add package Polly.Core`.

## 1. Власний тип винятку

Предметна область — склад інтернет-магазину. Виняток `InsufficientStockException` кидається, коли підтверджене замовлення неможливо зарезервувати через нестачу товару.

```csharp
public class InsufficientStockException : Exception
{
    public string ProductName { get; } = string.Empty;
    public int RequestedQuantity { get; }
    public int AvailableQuantity { get; }

    public InsufficientStockException()
        : base("Недостатньо товару на складі.") { }

    public InsufficientStockException(string message)
        : base(message) { }

    public InsufficientStockException(string message, Exception innerException)
        : base(message, innerException) { }

    public InsufficientStockException(string productName, int requestedQuantity, int availableQuantity)
        : base($"Неможливо зарезервувати {requestedQuantity} шт. товару \"{productName}\": у наявності лише {availableQuantity} шт.")
    {
        ProductName = productName;
        RequestedQuantity = requestedQuantity;
        AvailableQuantity = availableQuantity;
    }

    public int Shortage => RequestedQuantity - AvailableQuantity;
}
```

- Назва закінчується на `Exception`, клас успадковує `System.Exception`.
- Є три стандартні конструктори і четвертий — з контекстом помилки.
- Додаткові властивості дозволяють обробнику ухвалити рішення без розбору тексту повідомлення: у демонстрації за `Shortage` клієнту пропонується передзамовлення.

Демонстрація у `Main` (`TryReserve`) показує `try-catch-finally` з блоками `catch` від найспецифічнішого (`InsufficientStockException`) до загальнішого (`ArgumentException`). Блок `finally` виконується в усіх чотирьох випадках: успіх, нестача товару, неіснуючий товар, нульова кількість. Окремо показано загортання винятку в `InvalidOperationException` з `innerException`, щоб зберегти первинну причину.

### Коли кидати виняток, а коли повертати Result\<T\>

Виняток доречний, коли метод **не може виконати свій контракт** і ситуація для нього справді непередбачувана. `Warehouse.Reserve` викликається для вже підтвердженого замовлення. Якщо товару не вистачає, щось пішло не так (товар розібрали між перевіркою і оплатою), і продовжувати звичайний потік не можна. Виняток неможливо випадково проігнорувати, він несе стек викликів і контекст помилки. `Result<T>` доречний, коли неуспіх — **звичайний, очікуваний** результат. `Warehouse.CheckAvailability` перевіряє, чи можна купити товар на сторінці магазину, і відповідь «ні, доступно лише 3 шт.» тут така ж нормальна, як «так». Кидати виняток для неї було б повільно (розкрутка стека) і незручно: виклик довелося б обгортати в `try-catch` заради звичайної гілки `if`. Тому правило таке: валідація введення, пошук, що може нічого не знайти, перевірки бізнес-правил → `Result`/`bool`/`TryXxx`; порушення контракту, недоступні ресурси, пошкоджені дані → виняток.

## 2. Сценарій 1. Retry: тимчасово недоступний API курсу валют

**Проблема.** Застосунок отримує курс долара від зовнішнього API. Під час пікового навантаження API іноді відповідає `503 Service Unavailable`, але за мить знову працює. Якщо одразу показувати користувачу помилку, збій виглядає серйознішим, ніж є насправді.

**Стратегія:** Retry з експоненційною затримкою і jitter.
- Збій **тимчасовий**, тож повторна спроба має хороші шанси на успіх.
- Експоненційна затримка (200 → 400 → 800 → 1600 мс) дає перевантаженому сервісу час відновитися і не «добиває» його частими запитами.
- Jitter розносить у часі повтори від багатьох клієнтів, щоб вони не вдарили по сервісу одночасно.
- `ShouldHandle` обмежує повтори лише `HttpRequestException`: постійні помилки (`401 Unauthorized`) повторювати безглуздо.

```csharp
ResiliencePipeline pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<HttpRequestException>(),
        MaxRetryAttempts = 4,
        Delay = TimeSpan.FromMilliseconds(200),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = true,
        OnRetry = args =>
        {
            Log($"Retry #{args.AttemptNumber + 1} через {args.RetryDelay.TotalMilliseconds:F0} мс: {args.Outcome.Exception?.Message}");
            return default;
        }
    })
    .Build();

decimal rate = await pipeline.ExecuteAsync(token => api.GetUsdRateAsync(token));
```

**Опис виводу.** Показано три випадки:
- **а)** API двічі повертає 503. У логах видно `API: запит #1`, `Retry #1 через ~200 мс`, `API: запит #2`, `Retry #2 через ~400 мс`, `API: запит #3` і `Успіх: курс USD = 41,27 грн (усього запитів: 3)`. Затримки не рівно 200 і 400 мс, а з випадковим відхиленням — це jitter. Мітки часу в квадратних дужках показують, що пауза між спробами справді зростає.
- **б)** API недоступний довше, ніж дозволяє політика. Після 5 запитів (1 + 4 повтори) виняток передається далі і обробляється звичайним `catch`: застосунок показує курс із кешу.
- **в)** `401 Unauthorized` не потрапляє під `ShouldHandle`, тому Retry його пропускає без жодного повтору (`Без повторів (1 запит)`).

## 3. Сценарій 2. Circuit Breaker: база даних замовлень недоступна

**Проблема.** Сервер бази даних замовлень «впав» і буде недоступний кілька хвилин. Кожен запит чекає тайм-аут з'єднання, займає потік і повертає помилку. Якщо до цього додати Retry, кожен запит користувача перетвориться на кілька довгих очікувань, а після перезапуску сервер БД одразу отримає лавину накопичених запитів.

**Стратегія:** Circuit Breaker.
- Збій **тривалий**, тож повторювати кожен запит немає сенсу: серія помилок свідчить, що сервіс не працює.
- Після порогу помилок «автомат» розмикається (**Open**), і наступні запити відхиляються миттєво, без звернення до БД. Користувач одразу отримує відповідь, а сервер не навантажується.
- Через `BreakDuration` автомат переходить у **Half-Open** і пропускає один пробний запит. Якщо той успішний, автомат знову замикається (**Closed**).

```csharp
ResiliencePipeline pipeline = new ResiliencePipelineBuilder()
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<TimeoutException>(),
        FailureRatio = 0.5,
        MinimumThroughput = 4,
        SamplingDuration = TimeSpan.FromSeconds(10),
        BreakDuration = TimeSpan.FromSeconds(1),
        OnOpened = args => { Log($"Circuit OPEN: запити блокуються на {args.BreakDuration.TotalSeconds:F0} с"); return default; },
        OnHalfOpened = args => { Log("Circuit HALF-OPEN: пробний запит до БД"); return default; },
        OnClosed = args => { Log("Circuit CLOSED: БД відновилась, робота в звичайному режимі"); return default; }
    })
    .Build();
```

**Опис виводу.** Застосунок робить 8 запитів:
- запити **1–4** доходять до БД і завершуються `TimeoutException`. Після четвертого набирається мінімальна кількість запитів (4) з часткою помилок 100% ≥ 50%, і в лозі з'являється `Circuit OPEN`;
- запити **5–6** відхиляються миттєво (`BrokenCircuitException`), до БД не звертаються;
- перед запитом **7** сервер БД перезапускається, програма чекає 1,1 с (довше за `BreakDuration`). Запит 7 стає пробним: `Circuit HALF-OPEN` → успіх → `Circuit CLOSED`;
- запит **8** виконується звичайно.

Підсумковий рядок `Запитів від застосунку: 8, реально дійшло до БД: 6` показує ефект: два запити під час збою не навантажили сервер. У реальній системі з тисячами запитів за секунду ця різниця вимірювалась би тисячами.

## 4. Сценарій 3. Timeout + Retry + Fallback: повільний сервіс прогнозу доставки

**Проблема.** На сторінці оформлення замовлення показується прогноз доставки від стороннього сервісу. Інколи він «зависає» і відповідає за кілька секунд замість ста мілісекунд. Чекати так довго не можна: сторінка не відкриється, а прогноз — не критична інформація.

**Стратегія:** комбінація трьох стратегій.
- **Timeout (300 мс)** обмежує кожну окрему спробу, щоб повільна відповідь не блокувала сторінку.
- **Retry (2 повтори)** — повільна відповідь часто випадкова, і наступна спроба буде швидкою.
- **Fallback** — якщо всі спроби невдалі, користувач отримує типовий термін «2–4 дні» замість помилки. Сервіс не критичний, тому приблизна відповідь краща за жодну.

Порядок додавання важливий: **перша додана стратегія — зовнішня**. `Fallback` охоплює все, `Retry` повторює спроби, а `Timeout` всередині застосовується до кожної спроби окремо. Якби `Timeout` стояв перед `Retry`, обмеження в 300 мс діяло б на всі спроби разом.

```csharp
ResiliencePipeline<string> pipeline = new ResiliencePipelineBuilder<string>()
    .AddFallback(new FallbackStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>()
            .Handle<TimeoutRejectedException>()
            .Handle<HttpRequestException>(),
        FallbackAction = args => Outcome.FromResultAsValueTask("орієнтовно 2–4 дні (типовий термін, сервіс недоступний)"),
        OnFallback = args => { Log(...); return default; }
    })
    .AddRetry(new RetryStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>().Handle<TimeoutRejectedException>(),
        MaxRetryAttempts = 2,
        Delay = TimeSpan.FromMilliseconds(100),
        BackoffType = DelayBackoffType.Constant,
        OnRetry = args => { Log(...); return default; }
    })
    .AddTimeout(new TimeoutStrategyOptions
    {
        Timeout = TimeSpan.FromMilliseconds(300),
        OnTimeout = args => { Log(...); return default; }
    })
    .Build();
```

Timeout у Polly кооперативний: він скасовує `CancellationToken`, тому операція має цей токен поважати. Сервіс передає його в `Task.Delay(delay, token)`, і очікування справді переривається.

**Опис виводу:**
- **а)** перша спроба мала б тривати 800 мс, але через ~300 мс з'являється `Timeout: спробу перервано після 300 мс`, потім `Retry #1 через 100 мс`. Друга спроба (120 мс) успішна: `Результат: доставка до м. Рівне: 2 дні`. Загальний час ≈ 0,5 с замість 0,8 с.
- **б)** усі три спроби (800, 900, 1000 мс) перериваються тайм-аутом, після чого спрацьовує `Fallback`, і користувач отримує `орієнтовно 2–4 дні`. Загальний час ≈ 1,1 с замість 2,7 с очікування і помилки.

## 5. Інші патерни: Bulkhead

Bulkhead («перегородка») обмежує кількість одночасних звернень до ресурсу, щоб збій або повільність одного сервісу не забрали всі потоки застосунку. У Polly 8 його роль виконує стратегія `AddConcurrencyLimiter` з окремого пакета `Polly.RateLimiting`. У цій роботі вона не реалізована, але в сценарії 3 стала б наступним кроком: якщо сервіс прогнозу зависне для всіх користувачів, обмеження, наприклад, до 10 одночасних запитів не дасть йому заблокувати решту сторінок магазину.

## 6. Загальні висновки щодо Polly

**Переваги:**
- **Декларативність.** Політика описується конфігурацією (кількість спроб, затримка, пороги), а не вручну написаними циклами з `try-catch` і `Thread.Sleep`. Бізнес-код (`api.GetUsdRateAsync`) не змінюється взагалі.
- **Комбінування.** Стратегії складаються в один пайплайн (Fallback + Retry + Timeout), а порядок додавання визначає, як вони вкладаються одна в одну.
- **Готові перевірені реалізації** складних речей: експоненційний backoff з jitter, кооперативний тайм-аут, автомат з трьома станами і вікном вибірки — самостійно все це легко реалізувати з помилками.
- **Спостережуваність.** Події `OnRetry`, `OnOpened`, `OnTimeout`, `OnFallback` дозволяють логувати кожну спробу і зміну стану. Polly також інтегрується з телеметрією та `HttpClientFactory`.
- **Повторне використання.** Один пайплайн можна виконувати для багатьох викликів, а в ASP.NET Core — зареєструвати через dependency injection.

**Обмеження:**
- Polly не робить операцію безпечною для повтору. Retry неідемпотентної операції (списання коштів, відправлення листа) може виконати її двічі; за ідемпотентність відповідає розробник.
- Неправильні налаштування шкодять: занадто агресивний Retry посилює навантаження на сервіс, що й так не встигає, а занадто чутливий Circuit Breaker розмикається від випадкових поодиноких помилок.
- Timeout працює лише з кодом, що підтримує `CancellationToken`.
- Нова залежність і нова концепція в команді; складні комбінації стратегій важче налагоджувати.
- Polly лише маскує симптоми. Причини збоїв (перевантаження, помилки в коді) треба виправляти окремо, тому логування спроб, як у цій роботі, обов'язкове.

## Відповіді на контрольні запитання

1. **«Кидати виняток» чи «повертати Result».** Виняток — для ситуацій, коли метод не може виконати контракт: `Warehouse.Reserve` кидає `InsufficientStockException` для підтвердженого замовлення без товару; `File.ReadAllText` кидає `FileNotFoundException`. Result — для очікуваних неуспіхів: `Warehouse.CheckAvailability` повертає `Result<int>.Failure("Доступно лише 3 шт.")`; `int.TryParse` повертає `false` для некоректного рядка. Виняток неможливо проігнорувати, і він несе стек викликів, але він повільніший. Result швидкий і явно видний у сигнатурі, але його можна забути перевірити.
2. **Три стандартні конструктори:** без параметрів; з `string message`; з `string message` і `Exception innerException` (для загортання первинної причини).
3. **Circuit Breaker проти Retry.** Retry повторює операцію в надії, що збій тимчасовий; він доречний для коротких випадкових збоїв (мережа, 503). Circuit Breaker, навпаки, **припиняє** спроби після серії помилок і миттєво відхиляє запити, поки сервіс не відновиться; він доречний при тривалих збоях, щоб не навантажувати сервіс, що «впав», і не змушувати користувачів чекати тайм-аути. Часто їх поєднують: Retry для поодиноких збоїв усередині, Circuit Breaker для тривалих — назовні.
4. **Bulkhead** обмежує кількість одночасних звернень до певного ресурсу. Він вирішує проблему каскадного збою: повільний сервіс не може захопити всі потоки чи з'єднання застосунку, тож інші функції продовжують працювати.
5. **Навіщо Jitter.** Якщо багато клієнтів отримали помилку одночасно, без jitter вони повторять запити теж одночасно — через 1 с, 2 с, 4 с, — створюючи хвилі навантаження («thundering herd»), які не дають сервісу відновитися. Випадкова складова розподіляє повтори в часі.
6. **Ризики Retry для неідемпотентних операцій.** Операція могла насправді виконатися, а помилка виникла лише при поверненні відповіді (обрив з'єднання, тайм-аут). Повтор виконає її вдруге: подвійне списання коштів, дубль замовлення чи листа. Для таких операцій потрібні ключі ідемпотентності (сервер ігнорує повторний запит з тим самим ключем), перевірка стану перед повтором, або Retry застосовувати не можна.
