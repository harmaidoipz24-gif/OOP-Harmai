# Звіт до самостійної роботи №16

**Тема:** Колекції в практиці ООП: інвертований індекс і вимірювання продуктивності


## 1. Опис реалізації

### Структури даних

```csharp
// Слово -> множина ID документів
private readonly Dictionary<string, HashSet<int>> _index;

// ID -> документ (для швидкого отримання)
private readonly Dictionary<int, Document> _documents;
```

- `Dictionary<string, HashSet<int>>` за O(1) знаходить множину документів для слова.
- `HashSet<int>` гарантує, що документ буде записаний для слова лише один раз, навіть якщо слово повторюється в тексті, і дає готові операції над множинами для AND/OR-пошуку.
- `Dictionary<int, Document>` за O(1) перетворює знайдені Id на об'єкти документів.

### Нормалізація тексту (TextProcessor)

```csharp
private static readonly Regex WordRegex = new Regex(@"[\w#+]+", RegexOptions.Compiled);

public static IEnumerable<string> GetTerms(string text)
{
    return RemoveStopWords(Tokenize(text));
}
```

- Текст переводиться в нижній регістр (`ToLowerInvariant`), а регулярний вираз вибирає послідовності літер і цифр, тож пунктуація відкидається: `"async/await,"` → `async`, `await`.
- До шаблону `\w+` з методички додано `#` і `+`, бо інакше `C#` перетворювався б на `c`, і пошук `c#` знаходив би все підряд, де трапляється окрема літера «c».
- Стоп-слова (`a`, `the`, `is`, `and`…) видаляються: вони є майже в кожному документі і лише збільшують індекс.
- Слова **запиту** нормалізуються тим самим методом (`NormalizeWord`), тому `"C#"`, `"c#"` і `"C#,"` дають один і той самий результат.

### Пошук

```csharp
public List<Document> SearchMultipleWords(params string[] words)   // AND
{
    if (words.Length == 0)
        return new List<Document>();

    // Копія множини першого слова, щоб IntersectWith не зіпсував сам індекс
    HashSet<int> result = new HashSet<int>(GetDocumentIds(words[0]));

    for (int i = 1; i < words.Length && result.Count > 0; i++)
    {
        result.IntersectWith(GetDocumentIds(words[i]));
    }

    return ToDocuments(result);
}

public List<Document> SearchAnyWord(params string[] words)          // OR
{
    HashSet<int> result = new HashSet<int>();

    foreach (string word in words)
    {
        result.UnionWith(GetDocumentIds(word));
    }

    return ToDocuments(result);
}
```

Важлива деталь — **копіювання** множини перед `IntersectWith`. Якщо викликати `IntersectWith` прямо на множині з `_index`, перший же AND-запит видалив би документи з індексу назавжди. Також цикл AND зупиняється, щойно перетин став порожнім: далі він вже не зміниться.

Додатково реалізовано `SearchRanked` (завдання з зірочкою — ранжування): OR-пошук, де документи впорядковані за кількістю знайдених слів запиту. Для запиту `c# java popular` першим іде документ 5, що містить усі три слова.

Тестові п'ять документів дають **31 унікальне слово** (після видалення стоп-слів; у методичці 45 — там стоп-слова не видаляються і, ймовірно, інакше розбиваються складені слова).

## 2. Методика вимірювань

- Обидва підходи використовують **однакову нормалізацію** — `TextProcessor.GetTerms`. Лінійний пошук для кожного документа виконує ту саму токенізацію і видалення стоп-слів, що й індекс під час побудови. Програма порівнює кількість знайдених документів і виводить `(збігається)`.
- Колекції на 10, 100, 1000 і 10 000 документів генеруються з п'яти базових текстів з додаванням 5–14 випадкових слів зі словника. `Random(42)` з фіксованим seed робить дані відтворюваними.
- Шукане слово — `python`; воно є в 2 з 5 базових текстів, тому знаходиться рівно 40% документів (4, 40, 400, 4000).
- Один пошук через індекс триває менше мікросекунди, а `Stopwatch` для такого короткого інтервалу неточний. Тому пошук повторюється багато разів (100 000 для індексу, від 5 до 2000 для лінійного) і береться середній час.
- Перед вимірюванням виконується «прогрівний» виклик, щоб не враховувати JIT-компіляцію.
- **Окремо** вимірюється час побудови індексу, бо це разова ціна, яку лінійний пошук не платить.
- Програма запускалася командою `dotnet run -c Release -- --no-interactive`.

## 4. Аналіз

**Лінійний пошук** при кожному запиті проходить усі N документів і токенізує кожен з них регулярним виразом. Його складність — O(N · L), де L — середня довжина документа. Тому час зростає пропорційно кількості документів: у 10 разів більше документів — приблизно у 10 разів довший пошук.

**Пошук в індексі** — це один `TryGetValue` у словнику (O(1)) плюс формування списку знайдених документів (O(k), де k — кількість результатів). Час пошуку майже не залежить від загальної кількості документів, а лише від того, скільки з них містять слово. Через це прискорення зростає разом з обсягом колекції: на 10 документах різниця найменша, на 10 000 — найбільша.

**Ціна індексу.** Побудова індексу вимагає один раз токенізувати всі документи, тобто коштує приблизно як один лінійний пошук (O(N · L)), плюс вставки у словник. Крім того, індекс займає додаткову пам'ять: множину Id для кожного унікального слова.

**Поріг вигідності.** Оскільки побудова індексу коштує приблизно стільки ж, скільки один-два лінійні пошуки, індекс окупається вже після кількох запитів (колонка «Окупність»). Отже:
- якщо по колекції шукають **один раз**, індекс будувати немає сенсу — лінійний пошук простіший і загалом не повільніший;
- якщо пошуків **багато** (пошукова система, фільтр у застосунку), індекс вигідний навіть для невеликих колекцій, а на тисячах документів прискорює пошук на порядки;
- для **дуже малих** колекцій (≈10 документів) абсолютна різниця вимірюється мікросекундами і для користувача непомітна.

**Чинники, що впливають на вимірювання:** JIT-компіляція (тому є прогрів), конфігурація Debug/Release, збирання сміття (лінійний пошук створює багато тимчасових рядків), інші процеси на комп'ютері, кешування даних процесором. Тому окремі цифри можуть відрізнятися між запусками, але співвідношення між підходами залишається стабільним. Для точніших вимірювань варто використати BenchmarkDotNet.

## 5. Висновки

1. Інвертований індекс на `Dictionary<string, HashSet<int>>` дозволяє знаходити документи за словом за O(1) замість O(N · L) і будувати AND/OR-запити через `IntersectWith`/`UnionWith`.
2. Перевага індексу зростає зі збільшенням кількості документів, але він має разову ціну побудови і потребує додаткової пам'яті. Індекс вигідний, коли пошуків багато; для одноразового пошуку достатньо лінійного.
3. Коректне порівняння можливе лише за однакової нормалізації тексту. Інакше підходи знаходили б різні документи, і порівнювався б не лише час, а й різна робота.
4. Обмеження простої реалізації: немає стемінгу (`language` і `languages` — різні слова, тому документ 5 не знаходиться за запитом `programming language`), немає пошуку фраз і позицій слів, немає ранжування за релевантністю TF-IDF (лише проста кількість збігів у `SearchRanked`), немає виправлення помилок у запиті та синонімів, індекс зберігається лише в пам'яті і не підтримує видалення чи оновлення документів.

## Відповіді на контрольні запитання

1. **Чому `Dictionary<string, HashSet<int>>` підходить для інвертованого індексу?** Словник за O(1) знаходить множину документів за словом, а `HashSet<int>` зберігає кожен документ один раз і має вбудовані операції перетину та об'єднання.
2. **Переваги HashSet для AND/OR-пошуку.** `IntersectWith` (AND) і `UnionWith` (OR) працюють за лінійний час від розміру множин, оскільки перевірка наявності — O(1). Дублікати прибираються автоматично, а код пошуку займає кілька рядків. Зі списками довелося б вкладеними циклами порівнювати кожен Id з кожним — O(n·m).
3. **Чому важлива однакова нормалізація при вимірюванні?** Інакше підходи виконують різну роботу і знаходять різні документи: наприклад, лінійний пошук без зниження регістру не знайде `Python` за запитом `python`. Тоді порівняння часу некоректне, бо порівнюються різні алгоритми з різними результатами. Збіг кількості знайдених документів підтверджує, що порівняння чесне.
4. **Обмеження простої реалізації.** Немає ранжування за релевантністю (TF-IDF), стемінгу (`language`/`languages`) і підтримки фраз (порядок і сусідство слів не враховуються). Також немає обробки синонімів і помилок, оновлення чи видалення документів, а індекс живе лише в оперативній пам'яті.
